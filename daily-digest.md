## iOS Tips (Swift / SwiftUI)

### 1. Replace the deprecated single-param `onChange` closure

Several files (`SliderView.swift`, `BottomSheetView.swift`) still use the iOS 16 form deprecated in iOS 17:

```swift
// ⚠️ Deprecated in iOS 17
.onChange(of: props.value) { newValue in … }

// ✅ Preferred (iOS 17+) — receives both old and new value, no stale-capture risk
.onChange(of: props.value) { oldValue, newValue in … }
```

Wrap with `if #available(iOS 17, *)` to stay backwards-compatible. The two-param form eliminates a class of stale-closure bugs where the captured `self` value is from the previous render.
[Docs](https://developer.apple.com/documentation/swiftui/view/onchange(of:initial:_:)-8wgw9)

---

### 2. Replace `PreferenceKey` + `GeometryReader` with `onGeometryChange`

`BottomSheetView.swift` uses a custom `SizePreferenceKey` + `ReadSizeModifier` to read child size — a common but verbose pattern. iOS 17 introduced a one-liner:

```swift
// ✅ iOS 17+ — replaces ~30 lines of PreferenceKey boilerplate
.onGeometryChange(for: CGSize.self, of: \.size) { newSize in
    childrenSize = newSize
}
```

This reads geometry changes without needing a background `GeometryReader` layer, so it's cheaper to render.
[Docs](https://developer.apple.com/documentation/swiftui/view/ongeometrychange(for:of:action:))

### 3. `OptimizedFunction` uses Swift Macros for zero-cost type encoding

The `OptimizedFunction` added this week (`#44262`) attaches a `@OptimizedFunction` macro to module functions with primitive-type signatures. Instead of boxing arguments at runtime, the macro emits the type encoding **at compile time**:

```swift
// Regular — runtime boxing via reflection
Function("add") { (a: Int, b: Int) -> Int in a + b }

// OptimizedFunction — encoding generated by macro, no boxing
OptimizedFunction("add") { (a: Int, b: Int) -> Int in a + b }
```

If you're adding hot-path module functions (e.g. in `expo-modules-jsi`), prefer `OptimizedFunction` for measurable JS→Native throughput gains.

---

### 4. Use `@Observable` macro when you can drop iOS 16

The codebase uses `@ObservedObject` + manual `objectWillChange` today. iOS 17's `@Observable` macro is more granular — it re-renders **only** the views that read the changed property, not the whole observed object:

```swift
// iOS 17+ — precise per-property tracking, no @Published boilerplate
@Observable
final class SliderProps {
    var value: Float = 0
    var step: Float?
}
```

Worth planning for when Expo raises its minimum iOS version.
[Docs](https://developer.apple.com/documentation/observation)

## Android Tips (Kotlin / Jetpack Compose)

### 1. Use primitive state holders to avoid boxing

`SliderView.kt` already does this right — `mutableFloatStateOf` instead of `mutableStateOf<Float>`. The rule is general:

```kotlin
// ❌ Boxes Float on every state read/write
var value by remember { mutableStateOf(0f) }

// ✅ Uses FloatState — no boxing, less GC pressure
var value by remember { mutableFloatStateOf(0f) }
```

Kotlin Compose provides `mutableIntStateOf`, `mutableLongStateOf`, `mutableFloatStateOf`, and `mutableDoubleStateOf` for all four JVM primitives. Use them in any `ComposeProps` field or local composable state.
[Docs](https://developer.android.com/reference/kotlin/androidx/compose/runtime/package-summary#mutableFloatStateOf(kotlin.Float))

---

### 2. Annotate stable `ComposeProps` data classes with `@Stable`

Data classes like `SliderProps` that implement `ComposeProps` are structurally equal and predictable, but Compose's compiler doesn't always infer that. Marking them `@Stable` tells the compiler they can skip recomposition when the instance is the same:

```kotlin
@Stable
data class SliderProps(
    val value: Float = 0f,
    val min: Float = 0f,
    …
) : ComposeProps
```

This is a low-effort annotation that can meaningfully reduce recomposition count in lists like `LazyColumnView`.
[Docs](https://developer.android.com/reference/kotlin/androidx/compose/runtime/Stable)

---

### 3. Use `derivedStateOf` for values computed from other state

When a composable derives a value from one or more `State` objects (e.g. clamping a prop value), `derivedStateOf` memoizes the result and only re-runs the lambda when inputs actually change:

```kotlin
// Without derivedStateOf — recomputes on every recomposition
val clamped = props.value.coerceIn(props.min, props.max)

// ✅ With derivedStateOf — only recomputes when props.value/min/max change
val clamped by remember { derivedStateOf { props.value.coerceIn(props.min, props.max) } }
```

This pattern is especially valuable in `ModifierRegistry.applyModifiers` where modifier lists are rebuilt from props.
[Docs](https://developer.android.com/reference/kotlin/androidx/compose/runtime/package-summary#derivedStateOf(kotlin.Function0))

---

### 4. Batch slot-view lookups with `remember`

`BottomSheetView.kt` and `SliderView.kt` call `findChildSlotView(view, "...")` directly during composition. If the child tree hasn't changed, this is repeated work on every recomposition. Cache it:

```kotlin
// ✅ Only re-runs when the composable leaves composition
val thumbSlotView = remember { findChildSlotView(view, "thumb") }
```

If `findChildSlotView` can return different results as children change, use `remember(children) { … }` with the relevant key to invalidate the cache when needed.
